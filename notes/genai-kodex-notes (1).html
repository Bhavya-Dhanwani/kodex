The problem GenAI / LLMs solve

Before "how it works" — ask why it exists at all. Every real technology is a response to a limitation of what came before.

Traditional software only does what you explicitly coded for. A weather app can't answer a question you didn't design a button for. A search engine finds documents containing your words — it doesn't understand what you meant, it doesn't generate anything new, and it can't write, summarize, or reason.

A concrete example: the refund bot

Imagine you're asked to build a customer-support bot for an e-commerce site. With traditional code, you'd write something like:

if msg includes "refund"
→
send refund policy

Now a real user types: "bhai order galat aa gaya, paise wapas kaise milenge?" — no keyword "refund" anywhere. Your bot fails. You add "paise wapas". Then someone writes "money back". Then "return karna hai". You are now in an endless game of catching every possible phrasing — and you will always lose, because human language has infinite variations and your if-else has finite rules.

An LLM flips this. It wasn't given rules — it learned from millions of real conversations what "asking for a refund" looks like in every phrasing, every language, every typo. The intent is understood, not keyword-matched. That's the problem being solved: software that handles language it was never explicitly programmed for.

🎯 the actual gap

Computers were always good at storing and retrieving information. They were never good at producing language, understanding intent, or generalizing to new situations they weren't explicitly programmed for.

An LLM (Large Language Model) is the first widely usable tool that closes that gap. It isn't a database of answers — it's a model of how language works, trained on enough text that it can produce new, coherent, contextually appropriate text for situations it has never literally seen before.

What actually changed

BeforeNow, with an LLM
Rule-based chatbots — rigid decision trees, break on unexpected phrasingUnderstands intent even in messy, unstructured natural language
Search returns documents; you read and synthesizeSynthesizes an answer directly from what it has learned
Every new task needs new codeOne model generalizes across writing, coding, summarizing, reasoning
📌 the one-line definition

GenAI doesn't retrieve pre-written answers — it generates new content, token by token, based on patterns learned from massive amounts of text.

02 / 11

What is an LLM?

Before opening the machine, name it properly. LLM = Large Language Model. All three words carry weight:

Large

Billions of internal parameters (adjustable numbers), trained on trillions of tokens of text — books, code, websites, conversations.

Language

Its entire world is text. It reads text, it writes text. Anything expressible as text — code, JSON, essays, Hinglish — is fair game.

Model

Not a database, not a search engine — a mathematical function. Input goes in, probabilities come out. It stores patterns, not pages.

🎯 the simplest honest description

An LLM is autocomplete, scaled up to an extreme. Your phone keyboard predicts the next word from your last few words. An LLM predicts the next token from everything in its context window — and it learned its predictions from a large portion of all text ever written. Same idea, radically different scale, and at that scale something new emerges: coherent reasoning-like behavior.

📌 model vs product — don't confuse them

ChatGPT is a product; GPT is the model inside it. Le Chat is the product; Mistral is the model. In this course you're on the other side of that relationship — you build the product (MERN app), and the model sits behind an API you call.

How an LLM works — the big picture

Strip away the branding, and every LLM — GPT, Claude, Mistral, LLaMA — does exactly one job on repeat:

⚙️ the entire mechanism

Given the text so far, predict the single most likely next token. Add it. Repeat. That's it. There is no separate "understanding module" — understanding is an emergent side effect of getting extremely good at next-token prediction over trillions of words.

That one idea explains almost everything you'll learn today. Three building blocks control how that prediction loop behaves in practice — we'll open each one:

Tokens

The units the model actually reads and writes. Not words — pieces of words.

Context window

How much text (yours + its own past output) the model can "see" at once.

Temperature

How much randomness is allowed when picking the next token.

⚠ and one failure mode

Hallucination — because the model is always predicting "what token sounds right next," not looking up "what is factually true," it can produce fluent, confident, completely wrong answers. This isn't a bug that gets patched out — it's a direct consequence of how prediction-based generation works.

Tokenization — how text becomes numbers

Neural networks only do one thing at their core: matrix multiplication on numbers. They cannot "read" the letter A. So before anything else, all text has to become numbers.

🎯 why not just use whole words?

English has hundreds of thousands of words, plus names, typos, code, and every other language. A word-level vocabulary would be enormous and still miss words it's never seen. So models split text into subword tokens — common chunks that can be recombined to represent literally any string, even made-up ones.

A token is typically ~4 characters / ~¾ of an English word. Common words are often a single token ("the", "cat"). Rare or technical words get split into pieces ("tokenization" → "token" + "ization"). This is why LLM pricing and limits are measured in tokens, not words or characters.

Walkthrough
"Tokenization is powerful" → numbers
Step 1 · Raw string
"Tokenization is powerful"
This is what you typed. To a computer, right now, it's just a sequence of bytes.
Step 2 · Split into subword chunks
Tokenization is powerful
Notice "Tokenization" splits into two pieces (it's a less common word) while "powerful" stays whole. The splitting rule is learned from data ahead of time — it's called the tokenizer's vocabulary.
Step 3 · Each chunk → a fixed ID
1482728723186787
Every possible token has a fixed number in the model's vocabulary (often 30,000–130,000 entries). "Tokenization is powerful" is now just [14827, 2872, 318, 6787].
Step 4 · IDs become vectors
14827 → [0.02, -0.41, 0.88, …]
Each ID is looked up in an embedding table and turned into a long list of numbers (a vector) that captures meaning. This is the actual math the model operates on — everything before this step was just preprocessing.

⚠ practical consequence

Because you pay and are limited by tokens, not words: roughly, 1,000 English words ≈ 1,300 tokens. Code, Hindi, and other non-English scripts often tokenize less efficiently — more tokens for the same visible text.

Context window — what the model can "see"

An LLM has no memory between separate API calls. It doesn't remember your last message because it "recalls" it — it remembers because you (or your app) sent the entire conversation again, every single time.

🎯 the mental model

The context window is a fixed-size box. Everything the model uses to generate its next token — system prompt, chat history, your latest message, any documents you pasted — has to fit inside that one box, measured in tokens. Mistral Large, for example, ships a 128K-token window.

What happens when you exceed it

You can't send more tokens than the window allows. When a long conversation approaches the limit, applications typically do one of these:

StrategyWhat it does
TRUNCATEDrop the oldest messages to make room for new ones — the model "forgets" the start of the conversation
SUMMARIZEPeriodically compress old messages into a short summary, keep that instead of the full text
RETRIEVE (RAG)Store everything externally, pull back only the relevant pieces for each new message
✕ common confusion

A bigger context window is not the same as memory across sessions. Close the chat and open a new one — even with a 1M-token window, it starts empty unless your app explicitly re-sends prior context.

Temperature, top-p, and controlling randomness

At every step, the model doesn't pick just one "correct" next token — it computes a probability for every token in its vocabulary. "The sky is ___" might give blue (71%), clear (12%), falling (0.4%), and thousands more, all at once. Something has to decide which one actually gets picked.

🎯 temperature = how much risk to take

Low temperature (≈0–0.3): almost always pick the highest-probability token → focused, repeatable, safe answers. High temperature (≈0.8–1.2): lower-probability tokens get a real chance → creative, varied, sometimes weirder answers.

0.2

Top-p (nucleus sampling) — the other lever

Top-p works alongside temperature. Instead of considering the entire vocabulary, it narrows the field first: keep only the smallest set of tokens whose combined probability adds up to p (e.g. 0.9 = top 90% of probability mass), then sample from just that shortlist. It's a smarter cutoff than "always consider every token."

Try it
Prompt: "The sky is ___" — drag top-p, watch the shortlist shrink

Solid tokens are inside the nucleus — still in the running. Faded ones are cut and can never be picked, no matter how high the temperature.

Low temp + low top-p

Code generation, data extraction, JSON output — you want the same correct answer every time.

High temp + high top-p

Brainstorming, story writing, marketing copy — variety is the point.

Temp = 0

As close to deterministic as it gets — always the single most probable token.

How we use LLMs — local, self-hosted, or API

The model itself is the same idea everywhere. What changes is who runs the weights, and where.

ApproachWhat it meansTrade-off
LOCALModel runs on your own machine (e.g. via Ollama, LM Studio) — a small open model like Llama or QwenFree, private, offline — but limited by your hardware and generally weaker than frontier models
SELF-HOSTEDYou deploy an open-weight model on your own servers/cloud (e.g. on your AWS EKS cluster)Full control, data never leaves your infra — but you own the GPU cost, scaling, and uptime
APIYou call someone else's hosted model over HTTP — Mistral, OpenAI, Anthropic — pay per tokenZero infra, best models, instant scale — but you depend on their uptime, pricing, and data policy
📌 what we use in this course

We build on the Mistral API — no GPU to manage, frontier-quality models, and a generous free tier. This is also the most common pattern you'll meet in real MERN jobs: your Express backend makes an HTTP call to a hosted model, exactly like calling any other third-party API.

Structured output

An LLM's natural output is free-flowing text. That's great for a chat bubble — and useless if your Express route needs to save { name, price, category } to MongoDB.

🎯 the problem it solves

You can't reliably JSON.parse() a sentence like "Sure! Here's the product info you asked for: ...". Structured output forces the model to respond in a schema you define — usually JSON — so your code can consume it directly, no fragile string-parsing.

Two common ways to get there:

MethodHow it works
PROMPTINGYou instruct the model in plain English: "Respond only with valid JSON matching this shape: {...}" — works, but the model can still slip and add stray text
SCHEMA-ENFORCEDYou pass an actual JSON Schema / Zod schema to the API. The model is constrained at generation time to only produce tokens that form valid output — far more reliable
⚠ why this matters for MERN

Every real feature — "extract fields from this resume," "classify this support ticket," "generate a product description object" — needs structured output. This is the bridge between "the model can talk" and "the model can actually integrate into your backend."

Why and how we use LangChain & LangGraph

You could call the Mistral API directly with fetch(). For a single call, that's fine. The moment you need memory, tools, retries, multiple steps, or multiple models working together — hand-rolling all of that gets messy fast.

🎯 the problem LangChain solves

LangChain is a set of reusable building blocks — prompts, memory, output parsers, tool-calling, retrieval — so you're not reimplementing "keep conversation history" or "parse this into JSON" from scratch on every project. Same idea as Express giving you routing/middleware instead of raw Node http.

📌 the problem LangGraph solves

Real GenAI features aren't one call — they're a flow: "check intent → maybe call a tool → maybe loop back → then answer." LangChain alone is mostly linear (a chain). LangGraph lets you model this as an actual graph — nodes and edges, with conditionals and loops — which is what agents genuinely need.

11 / 11

Recap

the whole session in one loop

An LLM turns your text into tokens, fits them in a context window, predicts the next token over and over (shaped by temperature/top-p), and streams the result back — optionally forced into a schema, optionally orchestrated by LangChain/LangGraph, optionally run locally, self-hosted, or via API.

🎯 one thing to remember above all

Nothing here is magic. It's next-token prediction, at scale, with a few dials (temperature, top-p, context) that control its behavior. Everything you build on top — chatbots, agents, structured extraction — is engineering around that one loop.
